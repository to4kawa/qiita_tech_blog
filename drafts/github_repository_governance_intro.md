# GitHubをコード置き場で終わらせない

## 情シスのためのリポジトリ統制入門

GitHubは、開発者のための厨房である。

ただし、組織で使うGitHubは、ただの厨房ではない。そこには、麺も、スープも、仕込み表も、秘伝のタレも、自動調理機も、外部業者との連絡口も、店主権限も集まっている。

個人で作る一杯なら、多少散らかった厨房でも何とかなる。
だが、店として営業するなら話は変わる。

誰が厨房に入れるのか。
誰が寸胴を触れるのか。
秘伝のタレはどこに置かれているのか。
自動調理機は何をきっかけに動くのか。
外部の出前システムや仕入れ先とは、どこでつながっているのか。
味がおかしくなったとき、誰がどこを確認できるのか。

GitHub統制とは、開発者から包丁を取り上げる話ではない。
むしろ逆である。厨房をちゃんと店として回すために、入口、棚、鍵、仕込み、調理機、外部業者、記録を見えるようにする話である。

GitHubを「コード置き場」とだけ見ると、ソースコードの中身ばかりに目が行く。
しかし、情シスやセキュリティ担当者が見るべきなのは、一杯のラーメンだけではない。厨房全体である。

どの店舗が会社の管理対象なのか。
誰が厨房に入れるのか。
何が棚に置かれているのか。
どの機械が自動で動くのか。
その通常運用が、どんなリスクに変わるのか。
そして、そのリスクをどう統制し、どう監視するのか。

この記事では、GitHubを一軒のラーメン屋として見立てながら、情シス向けにリポジトリ統制の入口を整理する。

---

## 第1章：GitHubの境界を確認する

> **GitHub**
> ソースコードを置くだけでなく、権限管理、変更履歴、Issue、Pull Request、自動処理、外部連携も持つ開発基盤。

> **Repository**
> コードや設定ファイルを入れる単位。1つのシステム、アプリ、ライブラリ、ドキュメントごとの置き場。

> **Organization**
> 会社やチーム単位でRepositoryやメンバーを管理する入れ物。

> **Public / Private Repository**
> Publicは外部から見えるRepository。Privateは許可された人だけが見えるRepository。

まず見るべきは、厨房の境界である。

どこまでが自分の店なのか。
どこからが隣の店なのか。
どの厨房が本店管理なのか。
どの厨房が支店任せなのか。
どの屋台が、実は会社の看板を背負って営業しているのか。

GitHubで言えば、これはOrganizationとRepositoryの話である。

会社のOrganizationで管理しているRepositoryなのか。
個人アカウントが作ったRepositoryを業務で使っているのか。
外部委託先が管理しているRepositoryに、社内のコードや設定情報を置いていないか。
Public Repositoryとして外から見える状態なのか、Private Repositoryとして限定公開されているのか。

厨房の場所が分からなければ、衛生管理も、鍵の管理も、仕入れの確認もできない。

同じように、GitHubでも管理対象の境界が分からなければ、誰が触れるのか、何が置かれているのか、何が自動で動くのか、どのリスクに変わるのかを説明できない。

だからGitHub統制の入口は、コードレビューではない。

まず、どのOrganizationとRepositoryが会社の管理対象なのかを確認する。
それが、厨房の暖簾をくぐる前に見るべき最初の一歩である。

GitHub統制の入口は、まず管理対象の境界を明確にすることである。どのOrganization、Repository、公開範囲、外部管理Repositoryが会社の管理対象なのかが分からなければ、誰が触れるのか、何が置かれているのか、何が自動で動くのか、どのリスクに変わるのかを説明できない。

## 第2章：誰が触れるのかを確認する

> **Owner**
> Organization全体を管理できる最上位権限。メンバー追加、Repository設定、権限変更などに関われる。

> **Member**
> Organizationに所属する利用者。社員や社内開発者など。

> **Team**
> Memberをまとめる単位。部署、プロジェクト、役割ごとに権限を付けやすくするためのグループ。

> **Outside Collaborator**
> OrganizationのMemberではないが、特定Repositoryにアクセスできる外部ユーザー。委託先や外部協力者など。

厨房の場所が分かったら、次に見るのは「誰が入れるのか」である。

ラーメン屋で、厨房に誰でも入れる状態はまずい。客席に立つ人、仕込みをする人、麺を茹でる人、寸胴を任される人、レジだけ触る人、外部ヘルプで一日だけ入る人。役割が違えば、触ってよいものも違う。

GitHubも同じである。

ここでいう「触れる」とは、コードを読む、変更する、Pull Requestを作る、Repository設定を変える、Secretsを見る、Actionsを動かす、外部連携を設定する、といった操作を含む。

まず見るべきはOwnerである。OwnerはOrganization全体に強い権限を持つ。Ownerが多い状態とは、Organization全体を管理する必要がない人までOwnerになっている状態である。たとえば、各Repositoryの管理権限だけで足りる開発リーダー、異動後の元担当者、外部委託先の責任者、一時作業のために追加された人が、Ownerのまま残っている場合である。

Ownerが多すぎると、1人のアカウント侵害がOrganization全体の事故につながる。逆に少なすぎると、事故時に止められる人がいない。

次にMemberとTeamを見る。社員だから全部のRepositoryを見られる、という状態は望ましくない。Team単位で、必要なRepositoryにだけ必要な権限を付ける。異動や退職があったときに、Teamから外せば権限も外れる形にしておく。

Outside Collaboratorも重要である。委託先や外部協力者は、OrganizationのMember一覧だけを見ても見落とすことがある。契約が終わっても、GitHub上のアクセス権は自動では消えない。誰が、どのRepositoryに、どの権限で残っているかを確認する必要がある。

さらに、厨房に入るのは人間だけではない。

Bot、GitHub App、GitHub Actions、Personal Access Token、SSH key、Deploy key、AI Agentも、GitHub上では実質的に「触れる主体」になる。

流行りのAI Agentも、この観点で見る。

Claude Code、Codex CLI、Cursor Agentは、主に開発者本人のGitHub認証、SSH key、GitHub CLI認証、PATに乗る形でGitHubへ触る。つまり、GitHub上では「AI Agentが触った」というより、「その開発者の権限で操作された」ように見える場合がある。

GitHub Copilot coding agentは、GitHub側の操作主体として、Issue、Branch、Pull Requestに触るものとして見る。Bot、GitHub App、GitHub Actions系の延長に置くと理解しやすい。

Devinのような外部サービス型Agentは、GitHub連携、Bot的な権限、またはユーザーが与えた認証情報でRepositoryに触るものとして見る。

つまり、AI Agentは「賢い新人」では済まない。厨房に入って、仕込み表を読み、材料を切り、盛り付けまでできる存在である。誰の鍵で入っているのか、どの棚を開けられるのか、どこまで包丁を持てるのかを確認する必要がある。

GitHubの権限確認では、人間の利用者だけを見ても足りない。Owner、Member、Team、Outside Collaboratorに加えて、Bot、GitHub App、Actions、PAT、SSH key、Deploy key、AI Agentまで含めて、誰が、どの認証情報で、どのRepositoryに、何ができるのかを確認する必要がある。これは開発者リストではなく、情報資産へのアクセス主体の整理である。
