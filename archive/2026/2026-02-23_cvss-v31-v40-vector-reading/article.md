## 1. はじめに

本記事のゴールは、CVSS の指標を読んで「自分の環境での優先度判断に使える」レベルの読み方を身につけることです。  
スコアの値そのものではなく、ベクタ文字列（例：`AV:N/AC:L/PR:N/...`）から攻撃シナリオと影響範囲をイメージできるようになることを狙います。[1]

CVSS はベンダや NVD が公開する「技術的な深刻度」の共通フォーマットであり、そのまま自組織のリスクを示すものではありません。[2]  
優先度や期限を決めるには、環境固有の情報（どこに資産があり、どれだけ露出し、止まると何が止まるか）を別途加える必要があります。[2]  
本記事では、まず CVSS v3.1 / v4.0 の Base 指標の読み方を整理し、そのうえで AD と Siemens SINEC NMS の実例に当てはめ、「何を調べれば判断まで行けるか」をテンプレ化します。[3][4]

### TL;DR（忙しい人向け）

- v3.1は **AV / PR / UI → CIA → Scope** の順で30秒把握する
- v4.0は **AT → V\*（直撃）/ S\*（波及） → UI** で精密に読む
- 両方出ている場合は、**v3.1で全体像、v4.0で条件と影響を具体化**
- この記事では、即変換表と実例で“読める状態”まで持っていく

***

## 2. CVSSの全体像

CVSS は複数のメトリック群で構成されます。  
- v3.1：Base / Temporal / Environmental  
- v4.0：Base / Threat / Environmental / Supplemental  
本記事の主役は、通知やアドバイザリに必ず載る **Base 指標**です。[2]

重要なのは、「CVSS スコア ＝ リスク」ではなく、「CVSS はリスク判断の材料の 1 つ」という位置づけで見ることです。  
CVSS スコア単独でチケット優先度を決めない、という前提を置きます。[5]

***

## 3. CVSS v3.1：指標の見方

ここでは計算式には踏み込まず、Base ベクタから状況を説明できるようになることを目的にします。[1]

### 3.1 Exploitability（攻撃しやすさ）

- AV: Attack Vector（攻撃元区分）  
  - 何を見るか：攻撃者がどこから到達できるか。遠隔ほど危険。  
  - 情シス読み替え：公開範囲・到達性（Internet／社内／ローカル／物理）

- AC: Attack Complexity（攻撃の複雑さ）  
  - 何を見るか：成立に特殊条件が要るか。単純ほど危険。  
  - 読み替え：誰でも再現できるか／環境依存か

- PR: Privileges Required（必要権限）  
  - 何を見るか：攻撃前に必要な権限レベル。不要ほど危険。  
  - 読み替え：認証前か／ログイン必要か／管理者必要か

- UI: User Interaction（ユーザー関与）  
  - 何を見るか：ユーザー操作が要るか。不要ほど危険。  
  - 読み替え：クリック・開封・許可が必要か

- S: Scope（影響範囲）  
  - 何を見るか：権限境界を越えて別コンポーネントへ影響が波及するか。  
  - 読み替え：そのサービス内で終わるか／別の境界も突破するか

### 3.2 Impact（影響：CIA）

- C: Confidentiality（機密性）  
  - 何を見るか：どの程度情報が読まれるか。  
  - 読み替え：資格情報・個人情報・鍵・設定・設計情報などが漏れるか

- I: Integrity（完全性）  
  - 何を見るか：どの程度改ざんできるか。  
  - 読み替え：設定変更・データ改ざん・任意操作ができるか

- A: Availability（可用性）  
  - 何を見るか：どの程度止められるか。  
  - 読み替え：一時的劣化か、業務停止級か

***

**読む順番（最短ルール）**  
- AV → PR → UI：外から刺さる？ 認証いる？ クリックいる？
- C / I / A：漏れる？ 変わる？ 止まる？
- S：境界越えで波及する話か？（説明コストが跳ねる）

***

### 3.3 v3.1 ベクタ即変換表（汎用）

先ほどの内容を 1 つの表にまとめ、「どの CVE にも使える即変換表」として置きます。  
通知にあるベクタ文字列を、この表だけで日本語に変換できます。

**「Exploitability（攻撃しやすさ）」表**

| 指標 | 値 | ざっくり意味 | 情シスの即解釈（メモ） |
|------|----|-------------|------------------------|
| AV (Attack Vector) | N | ネットワーク越し | インターネット／社内NWから届く可能性。公開範囲確認を最優先。 |
|  | A | 近接NW | 同一セグメント／VPN配下など「近い」前提。到達経路が鍵。 |
|  | L | ローカル | 端末／サーバ上での実行が前提（ログイン・侵入後）。 |
|  | P | 物理 | 物理アクセス前提。拠点／筐体管理が論点。 |
| AC (Attack Complexity) | L | 条件が少ない | 再現容易、PoCが回りやすい。初動優先度が上がる。 |
|  | H | 条件が多い | 特殊条件／タイミング等。環境差で成立しない場合も。 |
| PR (Privileges Required) | N | 認証不要 | 認証前で成立し得る＝「外から刺さる」可能性が高い。 |
|  | L | 低権限必要 | 一般ユーザー／限定権限。侵入後の横展開起点になりがち。 |
|  | H | 高権限必要 | 管理者など前提。成立条件が重い（ただし内部不正には効く）。 |
| UI (User Interaction) | N | 操作不要 | 自動で成立し得る（スキャン→攻撃がそのまま成立しやすい）。 |
|  | R | 操作必要 | クリック／開封／許可が必要。教育・メール対策等も論点。 |
| S (Scope) | U | 境界内 | 影響は同一コンポーネント／同一権限境界に収まりやすい。 |
|  | C | 境界越え | 別コンポーネント／別権限境界へ波及し得る（説明で重要）。 |

**「Impact（影響：CIA）」表**

| 指標 | 値 | ざっくり意味 | 情シスの即解釈（メモ） |
|------|----|-------------|------------------------|
| C (Confidentiality) | N | 漏えいなし | 情報が読めない前提。 |
|  | L | 限定的漏えい | 一部データ／条件付き。対象データを具体化すると説明しやすい。 |
|  | H | 重大な漏えい | 資格情報・鍵・個人情報・設計情報など「広範／深刻」。 |
| I (Integrity) | N | 改ざんなし | 状態は変えられない前提。 |
|  | L | 限定的改ざん | 一部・制約付きの変更。影響範囲の特定が重要。 |
|  | H | 重大な改ざん | 設定変更・任意操作・任意コード実行等につながる。 |
| A (Availability) | N | 影響なし | 停止／劣化しない前提。 |
|  | L | 限定的停止 | 一時的・部分的な停止／劣化。 |
|  | H | 重大な停止 | サービス停止、復旧困難、業務停止級。 |

### 3.4 30秒トリアージの読み順

- 1. AV → PR → UI：外から刺さるか？ 認証いるか？ クリックいるか？
- 2. C / I / A：漏れる？ 変わる？ 止まる？
- 3. S：境界越えか？（波及がテーマになるか？）

この順で読むと、数式を知らなくても「危険そうか」「説明に何を入れるべきか」が 30 秒で見えます。

## 4. CVSS v4.0：指標の見方

### 4.0に入る前に：v3.1とv4.0のBase構造

![cvss_v32_v40_diagram_en.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/130729/3a66c886-5815-4bae-a616-e37d9040dae9.png)  
図1：CVSS v3.1 と v4.0 の Base 指標構造（Scope vs V*/S*）

v3.1 は Scope（S）で「境界を越えるか」を表現し、Impact は C/I/A で一括管理する設計です（速く全体像を掴むのに向く）。[1]  
v4.0 は「前提条件（AT）」と「直撃／波及（V*/S*）」を分けて書けるようにしたのがポイントです。[2]

### 4.1 Exploitability（攻撃しやすさ）

- AT: Attack Requirements（攻撃要件）  
  - 何を見るか：攻撃成立にターゲット側の前提条件が必要か。  
  - 読み替え：その前提（設定／状態／構成）が自社で成立するか？を明文化する枠。  

（AV / AC / PR は v3.1 とほぼ同じ意味で使いつつ、UI は None / Passive / Active の 3 値に分割。）[2]

| 指標 | 値 | 日本語変換 | 情シス読み替え |
|------|----|-----------|----------------|
| AV (Attack Vector) | N | ネットワーク越し | 外から届く（到達経路／公開範囲が最優先）。 |
|  | A | 近接ネットワーク | 同一セグメント／VPN等が前提。 |
|  | L | ローカル | 侵入後／ログイン等が前提。 |
|  | P | 物理 | 物理アクセス前提。 |
| AC (Attack Complexity) | L | 複雑さ低 | 再現容易・量産されやすい。 |
|  | H | 複雑さ高 | 回避／工夫／条件が必要。 |
| AT (Attack Requirements) | N | 追加前提なし | 「そのまま刺さる」寄り。 |
|  | P | 前提条件あり | 設定／状態／構成など「条件が揃うと成立」（自社で成立するか確認）。 |
| PR (Privileges Required) | N | 権限不要 | 認証不要（初動警戒）。 |
|  | L | 低権限必要 | 一般ユーザー等が前提。 |
|  | H | 高権限必要 | 管理者等が前提。 |
| UI (User Interaction) | N | 関与なし | クリック不要・自動成立寄り。 |
|  | P | 受動的関与 | 「非意図的」な関与で成立（例：閲覧だけ）。 |
|  | A | 能動的関与 | 実行／許可／承認など、意図して操作する必要あり。 |

※UI が None / Passive / Active の 3 値になったのが v4.0 の変更点。[2]

### 4.2 Impact（影響：直撃と波及）

- VC / VI / VA（Vulnerable System）  
  - 当該システムの機密性／完全性／可用性への影響。  
  - 読み替え：その製品・サービス自体がどうなるか。  

- SC / SI / SA（Subsequent Systems）  
  - 後続システム（波及先）の機密性／完全性／可用性への影響。  
  - 読み替え：踏み台になって周辺・下流に何が起きるか。  

v3.1 の Scope（S）で 1 ビット表現していた「境界を越えるか」を、v4.0 では V* と S* に分割して「どこにどれだけ効いているか」まで書けるようにした、と整理できます。[2]

| 指標 | 値 | 日本語変換 | 情シス読み替え |
|------|----|-----------|----------------|
| VC | N/L/H | 当該の機密性影響 | その製品・そのサービスから情報が漏れるか。 |
| VI | N/L/H | 当該の完全性影響 | その製品・そのサービスが改ざん／操作されるか。 |
| VA | N/L/H | 当該の可用性影響 | その製品・そのサービスが止まる／劣化するか。 |
| SC | N/L/H | 波及先の機密性影響 | 踏み台で周辺／下流の情報が漏れるか。 |
| SI | N/L/H | 波及先の完全性影響 | 踏み台で周辺／下流を改ざんできるか。 |
| SA | N/L/H | 波及先の可用性影響 | 踏み台で周辺／下流を止められるか。 |

※同じ P でも指標ごとに意味が違う（AV:P=物理、AT:P=前提条件あり、UI:P=受動的関与）ので、表の見出しとセットで読むと迷いにくくなります。

### 4.3 v3.1 Scope と v4.0 V*/S* の違い

- v3.1：Scope（S）で「境界を越えるか」を Unchanged / Changed で 1 ビット表現
- v4.0：Scope を廃止し、Impact 側を V 系（当該）と S 系（波及）に分けて、直撃と波及それぞれの CIA の大きさを書けるようにした

情シス視点では、v3.1 の S は「波及するか否か」のフラグどまりで説明材料が不足しがち、v4.0 の V*/S* は「直撃対応」「横展開対策」の会話に直結する、という差になります。[2]

## 5. 適用：指標の読み方を実例に当てはめる

ここから先は“読み方を当てはめる練習問題”パートです。

### 5.1 管理中枢系の例（Siemens SINEC NMS：CVE-2025-40736）

SINEC NMS は OT ネットワークの監視・管理を担う NMS で、中枢になりやすい製品です。[3]  
CVE-2025-40736 は、未認証で管理者資格情報（superadmin相当）を変更でき、結果として管理機能を奪われ得る脆弱性です。NVD では v3.1 と v4.0 のスコアが併記されています。[4]

- v3.1の読み下し（30秒メモ）：  
  `AV:N`（到達：ネットワーク）＋`PR:N`（認証不要）＋`UI:N`（操作不要）を見た時点で「外から刺さる」寄りのシナリオが立つ。  
  さらに `C/I/A` が高ければ、「管理中枢の奪取＝影響が広い」説明に繋げられる。

- v4.0の読み下し（深化）：  
  `AT` で前提条件の有無を確認し、Impact を `V*`（当該：NMS自体）と `S*`（波及：周辺ネットワーク）に分けて説明すると、関係者と会話が噛み合いやすい。

### 5.2 ID基盤の例（Active Directory：CVE-2021-42287）

CVE-2021-42287 は AD DS の権限昇格脆弱性で、NVD 上で NIST 評価と Microsoft（CNA）評価が併記され、AC（攻撃の複雑さ）が割れている例として読めます。[6][7]  
さらに KEV に掲載されているため、「実悪用」という運用上の強いシグナルとして扱えます。[8]

- v3.1の読み下し（30秒メモ）：  
  `AV:N`（ネットワーク）＋`PR:L`（低権限起点）＋`UI:N`（操作不要）なら、「侵害後の横展開・権限奪取」の会話に直結する。  
  ADは中枢なので、PRがNoneでなくても重く見える理由を説明しやすい。

- “情報源の読み方”としてのポイント：  
  ACが割れている＝「再現容易かどうか」の見立てが複数ある、という事実が読み取れる。  
  そして KEV があると、ACの議論より先に「優先度を上げる」根拠になりやすい。

## 6. 実務テンプレ：何を調べるか

ここは「対応手順」ではなく、「判断に必要な調査項目」をカテゴリ別に固定する章です。

### 6.1 共通の調査項目

どのカテゴリでも最小限、次を調べれば CVSS から判断まで持っていける、という共通セットです。

- 該当製品・バージョン・設置場所（どこにあるか）
- 露出（インターネット／VPN／社内限定等）
- 誰が到達できるか（認証・権限・経路）
- どんなデータ・機能に影響するか（CIA の具体化）
- 代替策／暫定策の有無（機能OFF・遮断等）
- KEV や実悪用情報の有無（運用上の上書き要因）[8]

### 6.2 カテゴリ別（ID基盤／境界／業務基盤／クライアント／管理中枢）

ここでカテゴリ A〜E を並べ、それぞれについて

- CVSS で特に注目する指標（＋具体ベクタ例を 1 つ）
- そのカテゴリ専用の「何を調べるか」チェックリスト

を置きます。

## 7. 最小フォーマット（読解メモ1枚）

最後に、1 つの脆弱性ごとに残しておくと便利な「読解メモ 1 枚」の枠を提示します。

- CVE / 製品名 / カテゴリ
- CVSS ベクタ（v3.1 / v4.0）
- 即変換 1 行メモ（AV/PR/UI/CIA または AT/V*/S* を日本語化）
- 調査結果メモ（6章の項目から要点だけ）
- 判断メモ（優先度・期限・根拠を 1 行）

*本記事では「ベクタを読む力」と「何を調べるかの型」をまとめました。  
あとは、自分の環境の CVE 通知にこのフォーマットをそのまま当てはめて、少しずつメモを貯めていくのがいちばんの近道です。*
